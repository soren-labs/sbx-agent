There are two ways in:

- **Use an existing deployment** — a teammate's or hosted control plane, like
  `https://sbx.sorenforge.com`. You need a base URL and an `sbx_` API key.
- **Self-host** — deploy your own control plane on your own Modal workspace
  in about 10 minutes.

<Tabs>
<TabItem label="Use an existing deployment">

## 1. Get an API key

Ask the operator for an `sbx_` key, or mint one yourself if you can reach the
console (**Settings → API keys**). Then:

```bash
export SBX_BASE_URL=https://sbx.sorenforge.com
export SBX_API_KEY=sbx_...
```

## 2. Run a task

```bash
curl -X POST "$SBX_BASE_URL/v1/tasks" \
  -H "Authorization: Bearer $SBX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "prompt": {"text": "Write hello.txt containing hi"},
    "source": {"repo": "https://github.com/owner/repo"},
    "delivery": {"pull_request": {}}
  }'
```

Or with the [Python SDK](/reference/python-client/):

```python
from sbx.sdk import SbxClient

client = SbxClient()  # reads SBX_BASE_URL + SBX_API_KEY
created = client.tasks.create(
    "Write hello.txt containing hi",
    source={"repo": "https://github.com/owner/repo"},
    delivery={"pull_request": {}},
)
task = client.tasks.wait(created.task.id)
print(task.status)
```

## 3. Watch it in the console

Open the deployment URL in a browser, or run `sbx open` from a machine with
the CLI configured. The task page streams the run live and shows the
delivered revision, its diff and the pull request.

</TabItem>
<TabItem label="Self-host on Modal">

## Prerequisites

- Python ≥ 3.12
- [uv](https://docs.astral.sh/uv/) (universal Python package manager)
- git
- A [Modal account](https://modal.com) (free tier works)
- At least one provider CLI installed and logged in locally

## 1. Clone and setup

<Steps>

1. Clone the repository:
   ```bash
   git clone https://github.com/soren-labs/sbx-browser.git
   cd sbx-browser
   ```

2. Install dependencies:
   ```bash
   uv sync
   ```

3. Authenticate with Modal:
   ```bash
   uv run modal token new
   ```
   This creates an interactive session. Alternatively, export `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET` in your environment (both required).

4. Initialize the config:
   ```bash
   uv run sbx init --providers codex,devin
   ```
   This creates `~/.config/sbx/config.toml` and scans for installed provider CLIs. Change `--providers` to match what you have installed (comma-separated: `codex`, `devin`, `antigravity`, `grok`, `opencode`).

</Steps>

## 2. Connect provider accounts

Each task runs a provider CLI inside a Modal sandbox, authenticated with a
credential you capture once. The easiest path is `sbx auth`, which runs the
provider's official login and imports the result:

```bash
uv run sbx auth login --provider devin
```

To reuse an existing login without re-authenticating:

```bash
uv run sbx auth import-existing --provider devin \
  --from ~/.local/share/devin/credentials.toml
```

Common credential locations:

| Provider | Login command | Credential file |
| --- | --- | --- |
| Codex | `codex login` | `~/.codex/auth.json` |
| Devin | `devin` (interactive) | `~/.local/share/devin/credentials.toml` |
| Antigravity | `agy` (OAuth) | `~/.gemini/antigravity-cli/antigravity-oauth-token` |
| Grok | `grok login` | `~/.grok/auth.json` |
| OpenCode | `opencode auth login` | `~/.local/share/opencode/auth.json` |

`uv run sbx auth status` shows what was found and each account's state; see
[Accounts and credentials](/guides/accounts/) for details.

## 3. Deploy

<Steps>

1. Deploy the control plane and images:
   ```bash
   uv run sbx deploy
   ```
   This:
   - Builds the runtime images (one per provider)
   - Seeds the durable Dicts (sessions, runs, tasks, accounts, etc.)
   - Creates the `sbx-control` Modal App
   - Runs a sanity check against the live control plane

   Output shows:
   - `SBX_BASE_URL`: your control plane endpoint
   - `sbx_<key>`: a new API key (written to `~/.local/state/sbx/bootstrap.key`, mode 0600)

2. Verify the deployment:
   ```bash
   uv run sbx doctor
   ```
   Should report all systems green.

</Steps>

## 4. Run your first task

<Steps>

1. Export the API key and base URL:
   ```bash
   export SBX_BASE_URL=<printed by sbx deploy>
   export SBX_API_KEY=$(cat "${XDG_STATE_HOME:-$HOME/.local/state}/sbx/bootstrap.key")
   ```

2. **Via curl:**
   ```bash
   curl -X POST "$SBX_BASE_URL/v1/tasks" \
     -H "Authorization: Bearer $SBX_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{
       "prompt": {"text": "Write hello.txt containing hi"},
       "execution": {"provider": "codex"}
     }'
   ```

3. **Via Python SDK:**
   ```python
   from sbx.sdk import SbxClient

   client = SbxClient()  # reads SBX_BASE_URL + SBX_API_KEY
   created = client.tasks.create(
       "Write hello.txt containing hi",
       execution={"provider": "codex"},
   )

   # Watch real-time events over SSE
   for event in client.watch(created.agent.id, created.run.id):
       print(f"{event.type}: {event.data}")
   ```

</Steps>

## 5. Follow up and deliver

Once a task is idle, send a follow-up to resume the same session:

```bash
curl -X POST "$SBX_BASE_URL/v1/tasks/{task-id}/runs" \
  -H "Authorization: Bearer $SBX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt": {"text": "Now make it executable (chmod +x hello.txt)"}}'
```

The run reuses the same sandbox and resumes the provider's native session
(e.g. Codex's thread ID stays the same). When the task worked on a
repository, publish the result with `POST /v1/tasks/{id}/delivery` — see
[Repositories, revisions and delivery](/guides/repositories/).

## 6. Open the console

```bash
uv run sbx open        # hands off already signed in
```

or serve the console locally against a fake backend (no Modal credentials
needed):

```bash
make console-dev     # then open http://localhost:8790
```

`make console-dev` starts a real local `/v1` control plane with fake
provider CLIs and a demo repository, serves the console, and prints a
throwaway API key — paste it into the Connect screen. See
[Web console](/guides/console/).
