<TabItem label="Use an existing deployment">

<a id="use-an-existing-deployment"></a>

You need only two values from the operator:

```bash
export SBX_BASE_URL=https://sbx.example.com
export SBX_API_KEY=sbx_...
```

### 1. Verify the connection

```bash
curl -fsS "$SBX_BASE_URL/v1/me" \
  -H "Authorization: Bearer $SBX_API_KEY"
```

A valid key returns its identity and scopes. If the call is rejected, fix the
key before creating work.

### 2. Preflight a repository task

Preflight resolves the repository and checks capabilities without allocating a
sandbox:

```bash
curl -fsS -X POST "$SBX_BASE_URL/v1/tasks/preflight" \
  -H "Authorization: Bearer $SBX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "prompt": {"text": "Fix the flaky date test"},
    "source": {"repo": "https://github.com/owner/repo"},
    "delivery": {"pull_request": {}}
  }'
```

For a private GitHub repository the operator must have connected the
[GitHub integration](/integrations/github/).

### 3. Create and wait for the task

```python
from sbx.sdk import SbxClient

client = SbxClient()  # reads SBX_BASE_URL + SBX_API_KEY
created = client.tasks.create(
    "Fix the flaky date test and add a regression test",
    source={"repo": "https://github.com/owner/repo"},
    delivery={"pull_request": {}},
)

task = client.tasks.wait(created.task.id)
print(task.id, task.status)
```

If you want live events, stream the current run:

```python
for event in client.runs.watch(created.agent.id, created.run.id):
    print(event.type, event.data)
```

### 4. Deliver, review and merge

A repository task produces durable revisions. Publish the latest revision,
record an independent approval, then merge:

```python
revision = client.tasks.deliver(created.task.id)
review = client.tasks.review(created.task.id, verdict="approve")
merged = client.tasks.merge(created.task.id)
print(merged.delivery)
```

The merge call fails closed if the approval is stale or not independent.
See [Repositories, revisions and delivery](/guides/repositories/).

<TabItem label="Self-host on Modal">

A fresh clone can deploy the platform before any provider is connected.
`./sbx` bootstraps `uv` and a managed Python environment when needed.

<Steps>

1. Clone and deploy:

   ```bash
   git clone https://github.com/soren-labs/sbx-browser.git
   cd sbx-browser
   ./sbx deploy
   ```

   On an interactive terminal, `deploy` initializes config and opens Modal
   authentication if no workspace login exists. A **zero-provider** platform
   deployment is valid.

2. Connect a provider:

   ```bash
   ./sbx auth login --provider devin
   ./sbx auth status
   ```

   The command runs the provider's official login/OAuth flow, captures the
   resulting credential, verifies it in the deployment and makes the account
   schedulable only after verification succeeds.

3. Connect GitHub when you need private repositories or pull requests:

   ```bash
   ./sbx github connect
   ```

   The first GitHub page is the official SBX GitHub App installation screen.
   Choose an account/repositories and click **Install** once. No PAT, PEM or
   per-deployment App registration is required for the default path.

4. Verify and open the console:

   ```bash
   ./sbx doctor
   ./sbx open
   ```

   `sbx deploy` writes the durable bootstrap admin key to
   `~/.local/state/sbx/bootstrap.key` and records the deployment URL in local
   state/config.

</Steps>

<Aside type="note">
`sbx init`, manual credential import, PATs and deployment-owned GitHub Apps
still exist for advanced/operator workflows. They are not required for the
normal fresh-deploy path.
</Aside>

Now use the same SDK or REST examples from the first tab.
