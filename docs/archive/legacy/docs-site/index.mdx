## Product model

The public workflow is deliberately small:

1. **Task** — the goal, optional repository, execution preference and delivery target.
2. **Run** — one execution turn; follow-ups reuse the same native provider session.
3. **Revision** — the durable code result pinned to an exact repository head.
4. **Delivery** — push a branch and optionally open/update a pull request.
5. **Review** — a verdict pinned to the exact revision head.
6. **Merge** — allowed only when the delivered head still matches a fresh independent approval.

Provider accounts, sandboxes, artifacts and workflow bindings still exist,
but they are implementation/advanced concepts rather than the primary way
to use the product.

## What SBX handles

<CardGrid>
  <Card title="Task execution" icon="open-book">
    Resolve the source repository, select an eligible provider account, run
    the task, queue follow-ups, cancel, retry, and keep terminal state.
  </Card>
  <Card title="Code delivery" icon="code-branch">
    Materialize revisions, push branches, open pull requests, detect stale
    reviews and enforce a review-gated merge.
  </Card>
  <Card title="Provider integrations" icon="database">
    Connect official provider logins and schedule across verified accounts
    with slot limits and failover.
  </Card>
  <Card title="GitHub integration" icon="external">
    Install the SBX GitHub App once for the repositories you choose. SBX
    mints short-lived installation tokens when a task needs them.
  </Card>
</CardGrid>

## What it is not

- **Not a model API.** Tasks run the official provider CLI under your subscription.
- **Not a hosted account service.** Credentials stay under your deployment's control.
- **Not a replacement for GitHub review.** SBX records its own exact-head review gate; GitHub remains the repository system of record.
