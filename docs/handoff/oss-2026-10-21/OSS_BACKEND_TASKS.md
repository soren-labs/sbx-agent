# SBX 开源版：服务端、MCP 与 API 工作包

日期：2026-10-21。状态：已准备工作包，当前先收尾 ENV；实际验证记录以 CODEX_HANDOFF.md 与 ENVIRONMENT_NOTES.md 为准。

## 执行范围

本轮先配置环境并交接任务，不由环境配置代理直接启动本表全部产品开发。后续由 Mac Codex 接手组织，**Claude Code 优先实现，Codex 独立验收**。用户已确定客户端由人工借助 Claude Design 等重新设计，本阶段保留原型并暂停客户端功能开发；SaaS 暂缓。

用户本次所说的“Cloud”指 **Claude Code** 开发执行者，不代表恢复 SaaS。本表是分阶段路线，不是自动同时启动所有工作包的指令；接手时先收尾 ENV，之后只安排首批 B1、B2、B4，并同步落实 B5。

继续使用 `soren-labs/sbx-agent` 的开源主线。沿用现有服务端、统一 API 和持久化基础，不另建平行核心；不把暂停 SaaS 解释为删除数据库、访问控制或凭证隔离。

## ENV：本轮环境与仓库交接

**目标：** Mac 能稳定统筹，Ubuntu 能执行开发与验证，用户订阅在开发 CLI 中可用。

- 配好必要工具、SSH、独立 checkout 和仓库锁定依赖，保留原工作区、审计资料及未提交原型。
- 用官方方式完成 Codex／Claude Code 开发订阅认证；已登录、调用成功、等待用户分别记录。
- 提供工具版本、准确路径、分支、基线、检查结果和持续任务重连方式。
- **当前状态：** Mac 环境和两机两家订阅调用已验证；Ubuntu 系统依赖／正式仓库／Linux 后端测试待 sudo 后续办。现有测试限制单独记录。
- **完成条件：** 交接表无含糊的“已配置”；每项有实测结果，未完成项有下一步。开发机登录不算 B3 完成。

## B1：自托管服务端可用基线

**目标：** 普通开发者可以在自己的机器启动 SBX 服务端并使用现有 API，不依赖 SBX SaaS。

- 复核现有运行方式，补齐首次启动、配置检查、状态查询、停止／重启和必要文档。
- 沿用当前业务核心及持久化；合理减少自托管的使用障碍，保留远端访问必要的控制。
- 使错误能区分服务不可达、配置缺失、认证失败和执行资源不可用。
- **验收：** 按文档在独立开发环境启动；创建并读取测试任务；重启后状态保留；必要依赖未就绪时返回明确诊断。
- **交付：** 可复现的启动说明、隔离配置示例、验证记录；不包含真实凭证。

## B2：常驻 Ubuntu／VPS 资源执行

**目标：** 将用户的一台常驻 Linux 工作站接入 SBX，作为真正的任务执行资源；同类 VPS 沿用同一流程。

- 覆盖机器接入、可用状态、任务派发、运行状态与结果、停止和断线后重新查看。
- 先在本次 Ubuntu 工作站完成；保留已有 Modal 能力。Local 开发执行器不直接等同于此工作包。
- 多项工作有清楚的归属与独立工作区；机器离线或执行失败不能呈现为成功。
- **验收：** Mac 主控经 SBX 派发真实文件／命令任务到 Ubuntu；主控断开再连接后可查询状态及结果；完成一次取消和一次可复现的离线处理。
- **交付：** 常驻资源使用说明、支持边界、真实执行证据及与 Modal 的回归结果。

## B3：官方订阅接入与兼容矩阵

**目标：** 用户自己的授权经对应官方 harness 在明确的资源上运行。优先补齐 Claude Code 订阅，再逐项扩展。

- 当前基线：Codex／Grok Build／Antigravity 有 Modal 订阅路线；Claude Code／OpenCode 的 API key harness 不能记成已完成订阅接入。
- 先完成 Codex＋Claude Code 在常驻机器上的真实使用；保留并验证已有 Modal 路线。
- 按工具记录安装、官方授权、授权状态、发起任务、读取输出、停止、后续继续和授权失效处理。
- OpenCode 先明确实际订阅来源、产品与认证方式，再形成可验收目标；无法核实的能力标为未验证，不以 API key 输入框替代订阅交付。
- 已有三家订阅从 Modal 扩展到常驻资源，必须单独验证；不能默认凭证或原生会话可跨资源任意迁移。
- **验收：** 使用真实用户授权完成真实任务；明确使用 subscription 或 API key，禁止为了通过而自动切换计费来源。
- **交付：** 五工具兼容表，按工具×认证方式×资源标记已验证／实验性／未支持；证据不含敏感数据。

## B4：可由外部 Codex／Claude 调用的 MCP

**目标：** 开发者把 SBX 配入常用工具后，可直接管理远端工作。

- 复用同一 API 与业务能力，提供可安装、可启动、可配置的外部 MCP 入口和说明。
- 首批工具覆盖：查看可用 harness／授权／资源、创建任务、查询状态、读取输出／结果、发送后续消息、取消任务。
- 工具调用能返回可追踪任务身份，不要求一个调用持续占住数小时；后续主控会话能找到已有工作。
- 区分本包与“给所有远端 harness 注入任意 MCP／skills”；后者不是本包完成前提。
- **验收：** 在 Mac 的真实 Codex 和 Claude Code 中配置并调用，派发至少一项远端工作，完成状态读取、后续消息、结果获取及取消。
- **交付：** 两种主控的实测配置指南、工具含义与错误说明、端到端证据。内部 HTTP 工具网关存在不算成品 MCP。

## B5：同一任务的 API／SDK／CLI／MCP 行为一致

**目标：** 用户从不同入口访问同一项任务，看到一致的状态、结果和可执行操作。

- 对 B2／B3／B4 涉及的能力同步更新 API、SDK、CLI、MCP、已实现规格及文档。
- 核实普通重试、重复提交、取消、恢复、分页／历史读取和权限不足的行为。
- 真实状态尚未确定时应明确呈现，不能误报完成或悄悄重复执行。
- **验收：** 从一个入口创建，另一个入口查询和操作；一次网络重试不造成额外任务；撤销访问后按约定拒绝后续调用。
- **交付：** 约定变更、兼容说明、代表性跨入口验证；遵守仓库已有生成与漂移检查。

## B6：长任务与跨机器联合验收

**目标：** 验证产品可以跨会话、跨天使用，不只完成几分钟的 PR。

- 外部主控派发至少两项有明确关系的工作，使用两个已验证 harness 与常驻／弹性两类资源。
- 记录总任务、子工作、等待事项、输出和结果位置，新主控能找到并接续管理。
- 覆盖客户端／主控断线重连、后续指令、取消、执行失败、服务端重启、资源生命周期结束及授权／额度不可用。
- 至少一次跨天运行；时长、资源与中断点按实测记录。当前 Modal 默认单沙箱六小时，不能只延长等待就宣称长期可靠。
- 明确区分：已派发工作继续、任务信息保留、后续阶段是否需主控判断；不要求首版另造无限自主规划代理。
- **验收：** 无丢失或重复的已确认工作；失败状态和恢复步骤可解释；代码与结果可取回；弹性资源按约定释放。
- **交付：** 一份连续流程记录、已验证的恢复边界和具体未覆盖事项。代码存在或假 provider 测试不能替代真实证据。

## B7：开源后端交付与发布准备

**目标：** 其他开发者能依照文档运行服务端，并从自己的 Codex／Claude 使用 API／MCP。

- 更新产品说明、自托管步骤、主控接入、支持矩阵、故障排查和版本变化。
- 提供可复现的安装／运行交付件，清楚标明所需依赖及已验证平台。
- 原有 PR／变更交付能力继续可用，任务结果不强制等于 GitHub PR。
- 许可证仍由用户确定；正式许可及发布元数据一致性属于公开发布前的决策，不能假定已有开源授权。
- **验收：** 独立验收者按文档完成首次启动、官方授权、MCP 派发、结果取回与重连；列出发布阻塞。
- **边界：** 准备可审查的发布候选；正式发布和生产部署按用户指示及仓库发布流程执行。

## R1／R2：扩展执行资源

Docker 和 Cloudflare 各自独立推进，先说明具体产品／运行环境，再复用统一资源与任务约定。Docker 服务端部署文件、Cloudflare Pages 发布都不能算已接入任务执行资源。

每包至少交付安装／认证／创建资源／执行任务／读取状态／停止／保留结果／清理流程，并说明生命周期、订阅兼容性和恢复边界。正式支持须通过 B6 的相关验收，不通过的组合如实标记，不阻止已验证组合形成可用版本。

每包提交时使用统一结果格式：**完成行为／代码与提交／验证／兼容边界／阻塞／下一步**。主控维护真实任务状态；通过仓库所需检查且无可复现 P0／P1 后结束本轮验收，不追求无限扩张的审查清单。
